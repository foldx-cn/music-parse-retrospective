# 折析 2.9.0：把 YunX 的账号与解析接进音乐解析

![封面](https://aka.doubaocdn.com/s/huBljyIxng)

> 本仓库保留《折析》（原《音乐解析》）的项目复盘、架构说明与版本记录；不包含具体实现源码。安装包通过官方下载页提供：<https://dl.foldx.cn/musicunlock-2.9.0.apk>。
> 项目仍在维护。本文只讨论工程结构、产品取舍和体验边界，不提供绕过版权、付费限制或平台登录的方法。所有转换都发生在用户自己的设备上，只针对用户合法拥有的音频文件。

## 2.9.0 更新了什么

2.8.4 的重点是下载中心；2.9.0 的重点是把入口收拢、把账号和解析接起来。

- 底栏「转换」改成「解析」；解析页分成「本地音频 / 链接解析」两段，粘贴分享链接后可以直接选平台、解析媒体、加入下载。
- 下载页改成集成进度：音频转换队列和下载任务放在同一个任务总览里，暂停、继续、重试、删除和完成路径都在这一页。
- 设置新增「账号与登录」：17 个平台按卡片排，支持备注、设为主账号、退出登录；点「登录」会在应用内打开平台网页，完成后回填 Cookie。
- 登录文件换成和 **YunX** 同格式的 `.yunx`：`YUNX_AUTH_V2` 头部、PBKDF2-HMAC-SHA256 210000 次、AES-256-GCM；兼容旧版 V1 的 10000 次迭代。
- 账号备份 schema 对齐 YunX：视频平台写成 `video:BILIBILI`、`video:XHS`、`video:DOUYIN`、`video:KUAISHOU`、`video:WEIBO`、`video:ACFUN`、`video:PIXIV`，字段包含 `id / cookie / nickname / isPrimary / remark / updatedAt`；网盘与 token 类平台保留各自字段。
- 下载任务支持每个任务单独携带 `Referer / User-Agent / Cookie / Origin`，B 站、Pixiv 等必须带来源的直链不会再直接 403。
- 图标换成蓝发耳机少女（方案一），桌面图标和网页 header 同步替换；名字继续用「折析」。

## 账号与登录

账号页的信息架构、登录方式和 `.yunx` 加密备份格式参考了 **[CYQawa/YunX](https://github.com/CYQawa/YunX)**。本 App 没有复制 YunX 源码，而是按它的备份格式做互通：导出的 `.yunx` 可以在两边互相导入，方便跨设备恢复。

登录入口在应用内用 Dialog + WebView 打开平台页面，登录完成后把 Cookie 回填到账号。账号只保存在本机，导出时才会生成加密文件；口令由用户输入，App 不保存明文口令。

## 平台解析

这一版先接了公开 HTTP 解析，按平台分派：

| 平台 | 状态 | 说明 |
| --- | --- | --- |
| B 站 | 已实测 | 返回单文件 mp4，标题、作者、封面、大小都能拿到 |
| AcFun | 已实测 | 返回 m3u8；目前保存播放列表，HLS 分片合并还没做 |
| 微博 | 已实现 | 需要登录 Cookie 才能稳定拿到视频 / 九宫格原图 |
| Pixiv | 已实现 | 需要登录 Cookie；原图必须带 Pixiv Referer |
| 快手 | 已实现 | 依赖页面 `INIT_STATE`，有风控风险 |
| 小红书 | 已实现 | 有登录墙，建议先登录；部分图片带水印 |
| 抖音 | 已实现 | 依赖 SSR 数据，抗风控能力弱 |

解析器、平台枚举和登录备份字段映射参考了 YunX 的实现；只处理公开可访问的页面，不碰登录态里的私有列表。平台改版或风控时，接口会返回失败原因，而不是假装成功。

## 下载中心

下载器沿用 2.8.4 的结构：Range 4 MB 分片、4 线程、暂停 / 继续、任务持久化和完成路径。2.9.0 增加了每任务 headers，HEAD、stream 和 Range 分片都会带上同一组 `Referer / User-Agent / Cookie`；解析结果里的 `headers` 会随「一键加入下载」一起传给后端。

夸克公开分享仍然只支持公开分享：先用分享短码换 `stoken`，再拉文件列表，最后对单个文件申请临时直链。游客直链的 CDN 必须带 `__pugs` Cookie，否则 412；这个 Cookie 只交给当前任务，不写进任务清单。

## 技术结构

整体仍然是「Android 壳 + 本地服务 + WebView 前端」：

- **Android 壳**：启动本地服务、承载 WebView、处理文件选择 / 保存 / 分享和生命周期。
- **本地 Python 服务**：只监听本机，处理文件识别、队列、转码、标签、落盘、账号和下载任务；数据留在设备上。
- **Java 编码层**：把耗时编码任务放进独立线程池，避免 Python 侧等待编码时卡住队列。
- **WebView 前端**：解析、下载、账号、设置、推荐、关于和更新日志都在这一层完成；桌面浏览器也能打开网页端。
- **更新源**：静态 `update.json`，只比对 `versionCode`；没有云端账号系统。

这套结构的好处是离线优先、数据在本地；坏处是四层技术栈，任何一层出问题，用户看到的都只是「转换失败」或「下载失败」。

## 没做好的地方

- **平台解析还窄**：只有 B 站、AcFun 实测通过；微博、Pixiv、快手、小红书、抖音还需要登录 Cookie 和更多真实链接验证。
- **AcFun 的 HLS 没合并**：目前只保存 m3u8 播放列表，没有把分片合成可播放视频。
- **隐藏 WebView 路线没接**：抖音、小红书、快手目前只有公开 HTTP 解析，抗风控能力弱。
- **真机覆盖不足**：应用内登录、Cookie 回填和 `saveText` 只做过编译和页面验证，真机矩阵还不够。
- **账号 token 类平台**：123、迅雷等 token 字段只在导入 / 导出时保留，WebView 登录仍以 Cookie 为主，跨 YunX 恢复 token 类账号可能失败。

## 边界

- 不提供绕过登录、付费墙或版权限制的功能；
- 不把第三方平台的内容做成可批量下载的资源库；
- 不在文章里写具体的绕过实现，也不在仓库里放安装包；
- 只讨论队列、格式、存储、性能、下载任务、账号备份和界面这些工程问题。
