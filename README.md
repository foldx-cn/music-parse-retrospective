# 音乐解析 2.0 → 2.8.4：在原来的壳里接上 YunX 的下载中心

![封面](https://img.foldx.cn/i/2026/11/14/1af82bc1d1.png)

> 本仓库保留《音乐解析》的项目复盘、架构说明与版本记录；不包含具体实现源码。安装包通过官方下载页提供：<https://dl.foldx.cn/musicunlock-2.8.4.apk>。  
> 项目仍在维护。本文只讨论工程结构、产品取舍和体验边界，不提供绕过版权、付费限制或平台登录的方法。所有转换都发生在用户自己的设备上，只针对用户合法拥有的音频文件。

## 2.8.4 更新了什么

2.8.4 没有把《音乐解析》改成一个“什么都能拿”的下载器。转换队列、解密、转码、保存目录、通知栏进度都没有变；原来的「转换 / 推荐 / 设置 / 关于」四个页面保持原来的配色、卡片、圆角和底栏阅读节奏，这次只在底栏多了一个「下载」入口。

下载中心的信息架构参考了 **[CYQawa/YunX](https://github.com/CYQawa/YunX)**。新增的平台识别、任务管理、分片续传和登录入口都来自这套开源实现；《音乐解析》只借鉴交互与行为，不复制 YunX 源码，并在下载页、更新日志和本文末尾标注来源。

### 下载页的四块内容

- **链接解析**：粘贴分享链接、直链或一段分享文案，自动识别平台、提取码和链接类型；覆盖 YunX 里的网盘、视频、图集平台清单。
- **媒体探测**：对公开网页读取 OG 封面、公开图片和音视频地址；只展示页面上已经公开的内容，不碰登录态里的私有列表。
- **网盘文件**：夸克公开分享会列出文件名、大小和目录标记；单文件「取直链」后直接进入下载任务，不转存到个人网盘。
- **下载任务**：Range 4 MB 分片、4 线程、暂停 / 继续、删除、任务持久化；下载完成后可以直接看到本机路径。

下载器本身不是这次才发明的。1.6.0 的《小说解析》已经做过一版下载中心；2.8.4 把它搬进《音乐解析》，并按音乐 App 的组件重新排了版。任务里的临时 Cookie 只留在内存里，任务列表和 `tasks.json` 都不会把它写出去。

### 夸克公开分享是怎么接的

先用分享短码换 `stoken`，再用 `stoken` 拉文件列表，最后对单个文件申请临时直链。测试用的公开分享是 `https://pan.quark.cn/s/fe29d0d39745`，返回 4 个 `.aar` 文件；其中一个 24,885,043 字节的文件，游客直链申请成功，下载后可以用 `unzip -t` 验证压缩包完整。

游客直链的 CDN 请求必须带 `__pugs` Cookie，否则会返回 412。App 只把这个 Cookie 交给当前下载任务，不写进任务清单；重启 App 后需要重新取一次直链。这不是“登录态”，只是游客临时凭证，所以不适合被当成永久下载地址。

```text
POST /api/netdisk/share   { url, password }
POST /api/netdisk/file    { shareId, stoken, fid, fidToken, name }
```

### 没有做的部分

这次没有适配 UC、迅雷、百度、移动云盘、123、115、蓝奏等网盘的私有文件列表，也没有适配抖音、小红书、快手、微博、AcFun、B 站、Pixiv 的私有视频 / 图集接口。它们仍然只有平台识别和登录入口；这不是“已经支持”，只是把入口先放在那里，后续再按平台逐个补。

同样没有做：绕过会员或付费内容、批量抓取登录后的私有资源、把直链长期缓存成可分享的资源库。下载器只能处理公开可访问的 URL；链接失效、平台风控或需要登录时，页面会给出失败原因，而不是假装成功。

## 它到底做了什么

到 2.8.4，它已经不只是一个“选文件 → 出结果”的按钮：

- **转换队列**：支持多文件排队，逐条显示进度、当前文件和完成数量；失败的文件不会被静默跳过。
- **输出选择**：可以选输出格式、压缩档位和保存目录；不想重新编码时，也可以保留原始音频流。
- **速度档位**：从高音质到极速，编码速度和文件体积之间可以自己取舍。
- **通知栏进度**：切到后台也能看到当前文件和完成数；完成、失败、清空队列都有明确状态。
- **推荐与更新**：内置推荐页、版本检查、更新日志和公告，至少让“这个版本改了什么”有地方可查。
- **反馈入口**：网页端有独立的反馈板，不要求注册，问题可以公开补充。
- **外观设置**：浅色/深色、底栏样式、毛玻璃、液态玻璃和界面缩放，尽量让工具看起来不像一个临时脚本。
- **下载中心**：2.8.4 新增，处理公开链接、公开分享和公开媒体，详见上一节。

这些功能里，真正每天会被用到的其实只有前几项。推荐、公告、反馈和主题，是项目逐渐“长出来”的部分，也是后来维护成本变高的原因。

## 技术结构

整体仍然是“Android 壳 + 本地服务 + WebView 前端”的结构：

- **Android 壳**：负责启动本地服务、承载 WebView、处理文件选择/保存/分享和生命周期。
- **本地 Python 服务**：只监听本机，处理文件识别、队列、转码、标签、落盘和下载任务；所有数据都留在设备上。
- **Java 编码层**：把耗时的编码任务放进独立线程池，避免 Python 侧等待编码时把整个队列卡住。
- **WebView 前端**：队列、设置、推荐、关于、下载和更新日志都在这一层完成；桌面浏览器也能打开网页端。
- **更新源**：一个静态 `update.json`，只比对版本号；没有账号系统，也不依赖云端数据库。
- **反馈板**：独立的小服务，负责收集公开反馈；和主程序解耦，挂了也不影响本地转换。

这套结构的好处是“离线优先、数据在本地”；坏处也很直接：Android 壳、Python 服务、Java 编码层和前端是四种技术栈，任何一层出问题，用户看到的都只是“转换失败”或“下载失败”。

## 最难的部分不是“转码”

真正做过之后，最难的是下面这些事：

1. **文件类型比想象中杂。** 容器、音频流、采样率、声道、裸 PCM、超大 WAV、不同平台的命名习惯，都会让“同一条转换链路”出现例外。一个格式能读，不代表能直接写；一个文件能播，不代表能被系统编码器接受。
2. **队列要让人安心。** 转换不是瞬间完成的，用户需要知道“现在到哪了、还剩几首、哪首失败了、失败原因是什么”。进度条如果只是装饰，反而会增加焦虑。
3. **并发和内存是跷跷板。** 并行数开大，速度上去了，内存也上去了；手机不是桌面，四路并行在千元机上很可能先把后台杀掉。
4. **Android 的存储不是普通文件系统。** 用户选择的目录要通过 SAF 持久化授权，写入失败还要有回退路径；文件名冲突、目录不存在、权限被回收，都是必须处理的正常情况。
5. **下载任务比转换多一层外部依赖。** 转换只依赖本地编码器；下载还要面对分享页改版、临时直链过期、CDN 412 和 Cookie 失效。任何一个环节失败，都要能把原因带回 UI，而不是只显示一个转圈。
6. **更新和反馈要形成闭环。** 版本检查、公告、更新日志、反馈板，看起来都不是核心功能，但它们决定了用户遇到问题时能不能找到答案。
7. **界面的一致性很难。** 队列、设置、推荐、关于、下载五个页面如果各写各的样式，最后就会变成一个“功能都在这、但不像一个 App”的拼装物。

这也是为什么后续版本把很多精力放在“状态”和“边界”上，而不是继续加格式：**能处理多少种文件不是唯一的价值，能不能让人清楚地知道发生了什么，才是。**

## 做对了什么，没做好什么

做对的地方：

- **本地优先**：没有账号、没有云端队列，文件不离开设备；下载任务也落在本机。
- **状态可见**：当前文件、完成数、失败原因、通知栏进度都在同一个语义下。
- **更新源简单**：一个静态 JSON 就够了，不需要为了检查版本再搭一套后端。
- **视觉统一**：底栏、卡片、主题和设置分组尽量保持一套语言，新增下载页没有破坏原来的阅读节奏。
- **边界写在明面上**：只处理用户合法拥有的文件和公开可访问的链接，不把“能解多少”当成卖点。

没做好的地方：

- **功能贪多**：推荐、公告、反馈、主题、更新日志、下载中心同时推进，核心链路的测试时间被稀释。
- **异常提示不够早**：有些格式是在转换开始后才报“不支持”，如果能在选择文件时就给出明确状态，体验会更好。
- **真机覆盖不足**：部分目录选择器和厂商 ROM 的行为只在代码层验证过，没有足够的真机矩阵。
- **下载适配还窄**：公开分享目前只真正打通了夸克；其它平台只有识别和登录入口，离“可用”还有距离。
- **并发默认值偏激进**：性能数据好看，但内存和后台存活是另一回事；默认值应该更保守。

## 边界与停不下来的维护

这个项目最容易走偏的地方，是把“本地工具”做成“内容入口”。一旦开始围绕“能拿到什么”做功能，产品就会从整理工具滑向内容搬运，接下来是无休止的站点适配、登录状态和规则变化。

所以现在的边界是明确的：

- 不提供绕过登录、付费墙或版权限制的功能；
- 不把第三方平台的内容做成可批量下载的资源库；
- 不在文章里写具体的绕过实现，也不在仓库里放安装包；
- 只讨论队列、格式、存储、性能、下载任务和界面这些工程问题。

这也是为什么这篇文章只能写到“怎么做这个工具”，而不能写成“怎么拿到某些文件”。后者不是工程问题，是版权和平台规则问题。

## 给后来者的几句话

1. **先做窄，再做全。** 队列、进度、失败原因、保存目录，这四件事做好，比再加十个格式更有用。
2. **把“不能做什么”写进产品。** 边界越早说清楚，越不容易被误解成“什么都能拿”。
3. **并发不是越高越好。** 手机上的性能优化，最后往往输给内存和后台存活。
4. **下载任务是外部世界的镜子。** 分享页会改、直链会过期、Cookie 会失效；把失败原因带回 UI，比偷偷重试更有用。
5. **更新源和反馈入口是产品的一部分。** 用户遇到问题时，能找到“这是哪个版本、有没有人遇到过”，比多一个功能更重要。
6. **不要用“技术中立”给自己找借口。** 工具的能力边界，最终要由做工具的人来划定。
